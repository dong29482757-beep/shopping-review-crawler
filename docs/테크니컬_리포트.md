# 테크니컬 리포트 — BeautyScope 서비스 설계

## 1. 문제 정의

화장품을 살 때 후기를 찾아보긴 하는데, 한 상품에 리뷰가 수백~수천 건씩
달려 있어서 다 읽고 판단하기 어렵다. "이 제품 보습은 좋은데 향이 별로다"
같은 속성별 평가를 한눈에 보여주면, 평점 하나만 보는 것보다 훨씬 유용한
의사결정 정보가 될 거라고 보고 시작했다.

## 2. 전체 아키텍처

```
[크롤링]                    [전처리/통합]              [분석 파이프라인]            [서비스]
coupang_crawler.py     →    merge_datasets.py     →    precompute_absa.py     →   app.py
crawl_images.py             (스키마 통일,                precompute_model_       (Streamlit)
                             라벨 재계산,                  sentiment.py
                             중복 제거)                   precompute_dashboard.py
                                                          precompute_skin_
                                                          segments.py
                                  ↓                              ↓
                         merged_reviews_all.csv         models/*.csv (집계 결과)
                          (538,774건, 단일 소스)          ml_logreg.joblib 등
```

ML/DL 학습과 무거운 연산(Okt 형태소분석, 모델 추론)은 전부 **사전 계산
(precompute)** 단계에서 끝내고, `app.py`는 미리 계산된 CSV만 읽어서 빠르게
보여주는 구조다. 화장품 리뷰 53만 건에 형태소분석을 매 요청마다 돌리면
사용자가 기다릴 수 없는 수준(초당 200건)이라 이 구조가 필수적이었다.

## 3. 데이터 파이프라인

### 3-1. 수집과 통합
3개 플랫폼(쿠팡 86,379건, 무신사 230,870건, 올리브영 221,525건)을 각각
다른 방식으로 모았다 — 쿠팡은 직접 크롤링, 나머지 둘은 동료가 수집한
데이터를 받아 통합했다. 컬럼 스키마가 셋 다 달라서 공통 스키마로 매핑하는
작업이 가장 까다로웠고, 특히 **무신사의 `sentiment` 라벨이 별점이 아니라
자체 텍스트 분석 기준**이라 5점 리뷰의 21%가 "부정"으로 잘못 라벨링되어
있던 걸 발견하고, 전체 데이터의 라벨을 별점 기준으로 통일해서 재계산했다
(원본은 `sentiment_text_raw`로 보존).

### 3-2. 속성기반 감성분석(ABSA)
`absa.py`: 정규식 키워드 매칭 + 부정어 처리 방식. 8개 속성(보습/수분, 향,
트러블/자극, 발림성/흡수력, 지속력, 가격/가성비, 용기/디자인, 효과)에 대해
리뷰를 문장 단위로 쪼개서(`split_clauses`) 각 절(clause)에 속성 키워드가
있으면 그 주변의 긍/부정 단어를 보고 판정한다. ML 분류기로 53만 건 전체를
돌리는 건 Okt가 병목이라 시간이 너무 걸려서, 빠른 규칙 기반으로 전체
데이터를 수 초 내에 처리하는 쪽을 택했다.

### 3-3. 모델을 핵심 결과에 통합 (가장 중요한 설계 변경)
처음엔 학습된 모델(TF-IDF+로지스틱회귀)이 비교실험에만 쓰이고 서비스
로직과 분리되어 있었다. "모델을 만들라니까 만든 느낌"이라는 피드백을
받고, 모델이 실제로 결과를 바꾸도록 파이프라인을 다시 짰다 (자세한 배경은
[발표_피드백.md](발표_피드백.md) 참고):

1. `precompute_model_sentiment.py`가 학습된 모델을 53만 건 전체에 돌려서
   "모델이 본 감성"과 "별점 기반 라벨"의 리뷰 단위 일치 여부를
   `review_match_flags.csv`에 저장
2. `precompute_absa.py`가 이 파일을 읽어서, 모델이 "불일치"로 판단한
   리뷰를 장단점/추천 계산 대상에서 **제외**
3. 결과적으로 사용자가 보는 "보습 92% 긍정" 같은 숫자 자체가 모델이 걸러낸
   데이터로 계산됨 — 모델을 빼면 다른 숫자가 나오는 구조

### 3-4. 랭킹 / 대안 상품 추천 / 피부타입 세그먼트
`report_data.py`에 계산 로직을 모아뒀다:
- `aspect_ranking()`: 카테고리+속성을 고르면 긍정비율 기준 Top N
- `find_alternatives()`: 어떤 상품이 특정 속성에서 약점이 있으면, 같은
  카테고리에서 그 속성이 margin(기본 10%p) 이상 더 좋은 상품을 찾아줌
- `skin_segment_view()`: 무신사 데이터에만 있는 피부타입 정보로, 같은
  상품이라도 피부타입별로 만족도가 다르게 나오는지 분리해서 보여줌

## 4. 모델 비교 실험

| 모델 | 정확도 | 비고 |
|---|---|---|
| ML (TF-IDF + 로지스틱회귀) | 0.738 | 확률보정(prior correction) 적용 |
| DL (numpy 직접구현 FFNN) | 0.762 | PyTorch 설치 제약(Python 3.14)으로 numpy로 직접 구현 |
| LSTM (PyTorch) | - | 별도 가상환경(torch_env)에서 학습 |
| KoELECTRA (파인튜닝) | - | Transformer 기반, 가장 무거움 |

공통적으로 neutral(중립) 클래스 분류가 가장 어려웠다 — 애초에 별점 3점
기준 라벨이 "약한 긍정"과 "약한 부정"이 뒤섞인 모호한 경계라서, 모델
성능의 한계보다는 라벨 자체의 모호성 문제로 판단했다.

## 5. 기술 스택

- Python, pandas/numpy/scikit-learn
- Streamlit (서비스 프레임워크)
- KoNLPy(Okt) — 한국어 형태소분석
- PyTorch (LSTM), Transformers (KoELECTRA) — 별도 가상환경에서 학습만, 서비스 구동에는 불필요(joblib/npz/safetensors로 추론만)

## 6. 한계와 의사결정 이유

- **속성별 감성 자체는 여전히 규칙 기반**이다. ML 모델이 아예 "속성 단위
  분류"를 학습하지 않았어서(8개 속성 라벨링된 학습 데이터가 없음), 모델은
  "이 리뷰가 신뢰할 만한가"를 걸러내는 데이터 품질 필터 역할까지만 한다.
  속성별 감성분류 자체를 모델로 바꾸려면 속성 단위로 라벨링된 학습 데이터를
  새로 만들어야 하는데, 이번 범위에서는 하지 않았다.
- **추천/랭킹 가중치는 통계적으로 학습된 값이 아니라 직접 정한 공식**이다.
  화장품 리뷰는 평점이 4~5점에 몰려 있어서(분산이 작음), 회귀로 가중치를
  자동으로 찾아도 신뢰할 만한 결과가 나오기 어렵다고 판단했다.
- **모델 기반 리뷰 제외는 다소 거친 방식**이다. confidence 기반 가중치
  같은 더 정교한 방법으로 개선할 여지가 있다.
- 원본 크롤링 CSV(쿠팡 중간 체크포인트 등)는 저장소에 포함하지 않고
  최종 정제 데이터(`merged_reviews_all.csv`)만 포함했다.
